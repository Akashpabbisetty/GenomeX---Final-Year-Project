## Part 1 — THE LIVE APP

### `engine/` — The rule engine (DO NOT edit without understanding)

This is the deterministic logic that evaluates a patient against every drug.
It is pure JavaScript with no external dependencies.

**Key files:**
```
engine/
├── index.js         ← entry point; call evaluatePatient() or evaluatePatientAsync()
├── dataset.js       ← loads and validates all the JSON from data/
├── evaluators.js    ← applies each rule to the patient
├── aggregator.js    ← combines rule results into the final 7-category outcome
├── explanations.js  ← generates the plain-language explanation text
└── reports.js       ← formats the output for the UI
```

**What is safe to touch:** Nothing in engine/ unless you understand the full
evaluation pipeline. A mistake here silently changes every drug recommendation.

**What to do instead:** If you want to change how a *rule* works, edit the rule
JSON in `data/rules/` (see below). If you want to change what the UI shows,
edit `frontend/`. The engine itself rarely needs touching.

**How to check you haven't broken it:**
```powershell
node --test "tests/*.test.js"    # must say all pass, zero fail
npm run validate-data            # must exit with no errors
```

### `data/` — The knowledge base (the safest place to make changes)

This is where the actual pharmacogenomic knowledge lives. All files are JSON.
The engine reads these at startup.

```
data/
├── rules/           ← ← THE RULES — this is what you edit to add/change clinical guidance
│   ├── pgx.json     ← pharmacogenomic rules (gene × drug × phenotype → category)
│   ├── allergy.json ← allergy-based rules
│   ├── renal.json   ← kidney function rules
│   ├── hepatic.json ← liver function rules
│   └── pregnancy.json
│
├── guidelines/      ← ClinPGx annotations (217 entries — READ ONLY, do not edit)
│   └── index.json   ← master index; individual annotation files in subdirectories
│
├── adverse/         ← SIDER side-effect data (READ ONLY — auto-generated by ingest)
│   ├── drug/        ← one JSON per drug (1,344 files)
│   └── by_term/     ← same data, indexed by effect term
│
├── tggates/         ← TG-GATEs preclinical data (READ ONLY)
│   └── index.json
│
├── evidence.json    ← evidence record index (E-* IDs used by rules)
├── drugs.json       ← master drug catalog (1,418 drugs)
├── genes.json       ← gene definitions
├── gene_catalog.json
├── vocab.json       ← shared vocabulary (phenotype terms, categories)
├── sources.json     ← data provenance (hashes, licences — update when you ingest new data)
│
├── model/           ← ML model scores land here after training
│   └── assoc_scores.parquet   ← created after you run research/kg/ on your ML machine
│
├── interactions.json          ← drug-drug interactions (NOT CONFIGURED — no licensed dataset)
└── LICENSE-DATA.md            ← data licence summary (ClinPGx, SIDER, TG-GATEs)
```

**SAFE to edit:** `data/rules/*.json` — add or modify rules here.
Every rule MUST have:
- A `drug` field matching a drug ID in `drugs.json`
- A `gene` and `phenotype` matching entries in `genes.json` / `vocab.json`
- An `evidence` array citing real E-* or G:PA* IDs from `evidence.json`
- A `category` of: avoid / modify / conditional / monitor / needs_info / informational / no_flag
- After editing, run `npm run validate-data` — it will catch schema errors

**DO NOT edit:** `guidelines/`, `adverse/`, `tggates/` — these are ingested from
external sources by scripts. Manual edits will be overwritten next time ingest runs.

**What happens if you add a rule incorrectly:**
- `npm run validate-data` will fail and tell you which field is wrong
- The engine will reject the whole file at startup and show no results
- Fix the JSON and re-run validate-data until it passes

### `tests/` — The automated tests (run these often)

```
tests/
├── engine.test.js          ← tests the rule engine logic
├── data.test.js            ← tests that data files are valid
├── ui.test.js              ← tests the UI components (needs jsdom / npm install)
├── server.test.js          ← tests the /api/evaluate endpoint
└── fixtures/
    └── reference_cases.js  ← ← THE REFERENCE CASES — one case per rule, with source citations
```

**The most important file here:** `reference_cases.js` — it contains one
hand-written test case per clinical rule, each citing its source. This is
what proves the rules are correct. If you add a rule to `data/rules/`, you
MUST add a matching reference case here.

**How to run tests:**
```powershell
node --test "tests/*.test.js"    # run from the project root
```

**Expected output:** all tests pass. If you see failures:
- If `engine.test.js` fails → you broke a rule (check your last change to `data/rules/`)
- If `data.test.js` fails → schema error in a data file (run `npm run validate-data` for details)
- If `ui.test.js` fails and you haven't run `npm install` → expected, it needs jsdom
- If `server.test.js` fails → API server issue

## The "what breaks what" cheat-sheet

| If you change... | What might break | How to check |
|---|---|---|
| `data/rules/*.json` | Rule engine output — wrong recommendations | `node --test "tests/*.test.js"` + `npm run validate-data` |
| `engine/*.js` | Everything — the whole evaluation pipeline | Same tests + manual test in browser |
| `data/drugs.json` | Drug catalog — drugs may disappear from UI | `npm run validate-data` |
| `data/evidence.json` | Rules that cite the changed evidence IDs | `npm run validate-data` |
| `data/guidelines/` | Guideline pointers shown alongside rules | `npm run validate-data` |
| `frontend/ui/*.js` | UI display, form behaviour | Visual check in browser + `ui.test.js` |
| `frontend/styles.css` | Visual only — nothing functional | Visual check in browser |
| `tests/fixtures/reference_cases.js` | Test suite — tests may fail or give false confidence | `node --test "tests/*.test.js"` |
| `research/kg/*.py` | ML training pipeline only — app is unaffected | Run `python research/kg/build_graph.py` |
| `genomex-final/` | Nothing — it's a copy, not the source | — |
| `scripts/` | Ingest/metrics scripts — app unaffected | Re-run the specific script |

## The golden rule

> Before and after ANY change, run:
> ```powershell
> node --test "tests/*.test.js"
> npm run validate-data
> ```
> If both pass, you haven't broken anything. If either fails, undo your change
> and read the error message — it will tell you exactly which file and line.

## Common tasks — step by step

### "I want to add a new drug rule"
1. Find the drug's ClinPGx guideline annotation ID in `data/guidelines/index.json`
2. Add an evidence record to `data/evidence.json` if one doesn't exist (format: `"E-YOURID": { "source": "...", "url": "...", "description": "..." }`)
3. Add the rule to the relevant `data/rules/*.json` file (copy the format of an existing rule)
4. Add a reference test case to `tests/fixtures/reference_cases.js` (copy an existing case format, cite the source)
5. Run `npm run validate-data` — fix any errors it reports
6. Run `node --test "tests/*.test.js"` — confirm your new test passes and nothing else broke
7. Update `PROGRESS.md` with what you added

### "I want to run the app"
```powershell
npm run serve
# open http://localhost:8000/frontend/genomx-advisor.html
```

### "I want to run the API"
```powershell
node genomex-final/api/server/index.js
# POST to http://localhost:8080/api/evaluate
```

### "I want to start ML training on my ML machine"
1. Copy `genomex-final/ml-package/kg/` to your ML machine
2. Copy the project's `data/` folder alongside it
3. Open `SETUP.md` in that folder
4. Follow it step by step (create venv, install deps, run `python run_all.py`)
5. Copy back `data/model/assoc_scores.parquet` and `figures/`

### "Something broke and I don't know what"
1. Run `node --test "tests/*.test.js"` — the failure message names the file and test
2. Run `npm run validate-data` — the error names the JSON file and field
3. Check `git diff` to see what changed recently
4. If you're stuck, open this file and find the row for what you changed in the "what breaks what" table
